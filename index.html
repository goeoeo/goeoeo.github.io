OpenCode MCP 服务器功能介绍

本文档介绍 opencode 中已接入的 MCP（Model Context Protocol）服务器及其各自的作用。MCP 是开放协议，让 AI 助手能够对接外部工具、代码、文档和知识库。

1. ast_grep — 代码结构化搜索与改写

是什么：基于 AST（抽象语法树）的代码搜索和批量改写工具，不是简单的文本正则匹配。

典型用途：

  • 按语法结构调整代码模式，例如把 console.log($MSG) 批量改成 logger.info($MSG)；
  • 支持 25 种编程语言，元变量（$VAR / $$$）匹配整个语法节点而非子字符串；
  • 干跑（dry-run）模式可先预览改动再应用，适合安全重构。

2. codebase-memory-mcp — 代码库知识图谱

是什么：为代码库建立索引的知识图谱工具，能理解函数、类、路由、模块之间的调用与依赖关系。

典型用途：

  • search_graph：按名称/语义搜索函数、类、变量；
  • trace_path：追踪「谁调用某函数」「某函数调用谁」、数据流向、跨服务调用；
  • get_architecture：查看项目模块划分、依赖、热点、架构边界；
  • query_graph：用 Cypher 查询复杂多跳关系、内聚度、复杂度分析。

适用场景：架构梳理、调用链追踪、影响面分析、死代码识别。

4. context7 — 库文档检索

是什么：检索最新、权威的第三方库 / 框架 / SDK 官方文档。

典型用途：

  • 查 API 语法、配置方式、版本迁移、库特定调试、安装说明；
  • 优先于凭记忆作答，避免训练数据过时；
  • resolve-library-id 先解析出库 ID，再用 query-docs 查具体问题。

5. grep_app — GitHub 真实代码检索

是什么：从超过百万个公开 GitHub 仓库中检索真实代码示例（可理解为 GitHub 全局 grep）。

典型用途：

  • 查某个库/API 的真实用法、生产级实现范例；
  • 按语言、仓库、文件路径过滤；
  • 支持正则匹配跨行模式，适合「别人怎么实现某功能」的问题。

6. lsp — 语言服务器协议集成

是什么：通过 LSP（Language Server Protocol）提供编辑器级的代码智能能力。

典型用途：

  • 诊断：获取文件/目录的错误、警告、提示（diagnostics）；
  • 跳转：找定义（goto_definition）、找引用（find_references）；
  • 重命名符号、查文档/大纲符号；
  • 用于改码后验证语法、做安全重构。

8. websearch — 网页搜索与抓取

是什么：联网搜索并按需抓取网页内容，转换为 Markdown 等格式供 AI 使用。

典型用途：

  • 搜索最新信息、新闻、事实、人物、公司；

Skill 使用规则要点

  1. 判断是否该用：只要有一丁点可能适用，就必须调用 skill 检查，不能跳过。
  2. 流程类优先：先加载流程类 skill（如 brainstorming、debugging）决定「怎么做」，再加载实现类 skill 指导「怎么执行」。
  3. 来源优先级：项目 > 用户 > opencode > 内置。用户安装的 skill 覆盖内置默认。
  4. 用户指令优先于 skill：用户明确的指示（CLAUDE.md/AGENTS.md/直接请求）始终优先级最高。

OpenCode 模型 Fallback 配置

默认模型为第三方中转 coreshub/DeepSeek-V4-Flash（openapi.coreshub.cn），相比 DeepSeek 官方直连偶发不稳定（实测日志中出现多次 Too Many Requests(429) 与 ProviderHeaderTimeoutError）。为保证主模型不可用时自动降级到官方 deepseek，配置了运行时 fallback。

机制说明

opencode 原生不支持 provider 自动 fallback。oh-my-openagent 插件（4.19+）内置两套机制：

机制 fallback 目标来源 适用性
model_fallback 硬编码链（AGENT_MODEL_REQUIREMENTS，如 sisyphus → claude-opus-5 / kimi-k3 / gpt-5.6-sol…） ❌ 会切到本环境未接入的模型，不可达项被跳过
runtime_fallback 用户配置 agents[].fallback_models ✅ 采用

选用 runtime_fallback：主模型仍为 coreshub，失败时自动切换到用户指定的 deepseek 官方模型。

配置

1. coreshub provider 能力声明（~/.config/opencode/opencode.jsonc）

经实测 coreshub 平台完整兼容 DeepSeek 官方接口（流式返回 reasoning_content、支持 tool_calls、reasoning_effort、temperature），因此补齐能力声明并调大超时，让 opencode 正确解析思维链、对齐官方直连体验：

2. runtime_fallback（~/.config/opencode/oh-my-openagent.jsonc）

字段说明：

字段 说明
enabled 总开关。也可简写为 "runtime_fallback": true
retry_on_errors 触发 fallback 的 HTTP 错误码，覆盖 coreshub 常见的 429 限流
max_fallback_attempts 单个会话最大 fallback 尝试次数（1–20），防死循环
cooldown_seconds 失败模型的冷却时间，冷却期内不再尝试它
timeout_seconds 无响应/超时场景的兜底判定
notify_on_fallback 切换模型时弹出 toast 提示
restore_primary_after_cooldown 冷却期过后自动恢复主模型 coreshub（保证「默认还是用它」）
agents[].fallback_models 该 agent 的 fallback 候选列表（string / string[] / [{model, reasoning, ...}]），按实际使用的 agent（build / sisyphus）配置

行为与触发流程

  1. 检测到可重试错误（默认 429/500/502/503/504，可自定义）或超时；
  2. 中止当前请求，从 fallback_models 中取下一可达且非冷却中的模型重发，并 toast 提示「Model fallback」；
  3. 若仍失败则继续取下一个候选（自动跳过与当前模型等价、以及被 disabled_providers 禁用的条目）；
  4. 达到 max_fallback_attempts 后停止，不再无限重试；
  5. 冷却期（cooldown_seconds）过后自动恢复主模型。

验证与注意事项

  • 校验方式：JSON 语法 + 插件 schema（oh-my-opencode.schema.json，注意其 required: ['git_master'] 是生成文件的 bug，插件实际用 zod 校验且全部字段可选）+ opencode models 启动加载无报错；
  • 端到端可用：opencode run -m coreshub/DeepSeek-V4-Flash "hi" 正常响应即配置生效；
  • 配置在 opencode 启动时加载，修改后需重启 opencode 生效；
  • 注意：model_fallback 使用硬编码链，不读用户 fallback_models，本方案刻意未启用它，避免主会话 fallback 到不可达模型。

colima 原理

colima 原理

colima 通过以下方式在 macOS 上提供容器运行时：

  1. 基于 Lima（Linux on macOS）启动一个轻量级 Linux 虚拟机
  2. 在该虚拟机内部运行 containerd 与 nerdctl，实现与 Docker CLI 兼容的接口
  3. 通过 Unix socket 将虚拟机内的 containerd 暴露给 macOS 主机，用户可像使用原生 Docker 一样执行 docker/nerdctl 命令
  4. 默认使用 QEMU 虚拟化，可选 VZ（Apple 原生虚拟化框架）以获得更好的性能与 Apple Silicon 兼容性
  5. 网络层通过 gvproxy 实现端口转发与 DNS 解析，使容器服务可直接通过 localhost 访问
  6. 卷挂载利用 virtiofs（或 sshfs）实现主机目录与虚拟机内目录的高效共享
  7. 整体架构无需安装 Docker Desktop，即可在 macOS 上获得接近原生的容器体验，并避免 Docker Desktop 的授权限制

关于宿主机能够直接ping通容器的问题

orbstack 能够直接ping通容器的问题，而colima 不能,这是因为:
Colima 使用的是传统的、嵌套的 NAT-on-NAT 模型。
OrbStack 使用的是先进的、扁平的 无缝桥接 模型。

Colima 的网络模型：NAT-on-NAT

Colima 的核心是启动一个完整的 Linux 虚拟机（通过 QEMU），然后在这个 VM 内部运行 Docker。这就造成了双重网络隔离：

第一层 NAT（虚拟机层）：你的 Mac 宿主机和 Colima VM 处于不同的网络。Colima VM 有一个虚拟网卡（如 eth0），它从 Hypervisor（QEMU）获取一个私有 IP（比如 192.168.64.X）。QEMU 负责在宿主机和 VM 之间进行 NAT。这就是为什么你从 Mac 上无法直接 ping 通 VM 的 172.17.0.2，因为这个网段在 VM 内部，没有被映射到宿主机。
第二层 NAT（容器层）：在 Colima VM 内部，Docker 又创建了自己的私有网络（docker0 网桥，如 172.17.0.1/16）。Docker 引擎通过 iptables NAT规则 将容器端口映射到 VM 的 IP 地址上。

OrbStack 的网络模型：无缝桥接（Virtio-networking）

OrbStack 从头开始设计，其核心目标就是实现 macOS 和容器/虚拟机之间的高性能和无缝集成。它没有使用传统的 QEMU NAT 模型。

扁平化网络：OrbStack 使用自定义的 virtio-networking 驱动，在宿主机 macOS 和轻量级 Linux VM 之间建立一个共享的、扁平的虚拟网络。这意味着：

OrbStack 的 VM 和你的容器直接位于你 Mac 的局域网中。
它们可以从你的 Mac 获得一个真实的、可路由的 IP 地址（通常是 192.168.64.X 网段），而不是一个双层 NAT 后的地址。
网络栈共享：OrbStack 的 VM 和容器共享同一个网络栈。从网络的角度看，它们更像是一台设备上的多个进程，而不是嵌套的隔离环境。Docker 的 bridge 网络（172.17.0.0/16）被巧妙地桥接并暴露到了 macOS 的网络环境中。

但orbstack是商业付费产品，而colima 是开源免费的。

  • endpoint_snitch: 节点的snitch
  • num_tokens: 节点的token数量
  • disk_failure_policy: 磁盘失败策略
  • commitlog_sync: 提交日志同步策略
  • commitlog_sync_batch_window_in_ms: 提交日志同步批量窗口时间
  • commitlog_segment_size_in_mb: 提交日志分段大小
  • commitlog_total_space_in_mb: 提交日志总大小
  • commitlog_roll_when_full: 提交日志满了是否滚动
  • commitlog_roll_when_full_in_mb: 提交日志满了滚动的大小
  • commitlog_roll_when_full_in_ms: 提交日志满了滚动的时间
  • commitlog_roll_when_full_in_bytes: 提交日志满了滚动的字节数

Casssandra基本概念

数据模型

列

列是cassandra的基本单位，具有三个值：名称，值，时间戳
在Casssandra中不需要预先定义列，只需要在KeySpace中定义列族，然后就可以开始写数据了。

列族 ColumnFamily

列族相当于关系型数据库的表，包含了多个列的容器

列族的2种类型：

  • 静态列族 字段名是固定的
  • 动态列族 字段名是动态的

Row key:列族中每一行都是一个key，key是唯一的，用来标识这一行数据。

主键：

  • 主键是用来唯一标识一行数据的
  • 主键可以由一列组成，也可以由多列组成

键空间 KeySpace

键空间是cassandra中最外层的容器，相当于关系型数据库中的数据库。
键空间中包含了多个列族，每个列族中包含了多行数据。
每个键空间中都有一个默认的列族，列族的名称为default。

键空间创建的时候可以指定一些属性：副本因子，副本策略，Durable_write(是否启用commitLog机制)

副本因子：

  • 副本因子是用来指定每个键空间中副本的数量的
  • 副本因子的默认值是1
  • 副本因子可以在键空间创建的时候指定，也可以在键空间创建之后修改

副本策略：

  • 副本策略是用来指定每个键空间中副本的分布策略的
  • 副本策略的默认值是SimpleStrategy
  • 副本策略可以在键空间创建的时候指定，也可以在键空间创建之后修改

Durable_write：

  • Durable_write是用来指定每个键空间中是否启用commitLog机制的
  • Durable_write的默认值是true
  • Durable_write可以在键空间创建的时候指定，也可以在键空间创建之后修改

副本

副本就是把数据存储到多个节点上，来提高容错性

节点

存储数据的机器

数据中心

多台机器组成一个数据中心

集群

Cassandra数据库是为跨越多条主机共同工作，对用户呈现为一个整体的分布式系统设计的。Cassandra最外层容器被称为集群。
Cassandra将集群中的节点组成一个环（ring）,然后把数据分配到集群中的节点上

数据类型

  • 数值类型
  • 文本类型
  • 时间类型
  • 标识符类型 例如UUID
  • 集合类型 例如set,list,map
  • 其它基本类型 例如boolean,blob,inet,counter
  • 用户自定义类型

CQL Shell客户端

CQL Shell是Cassandra提供的一个命令行客户端，用于执行CQL语句。
CQL Shell可以在Cassandra的安装目录下的bin目录中找到。
CQL Shell的使用方法如下：

  1. 进入Cassandra的安装目录下的bin目录
  2. 执行cqlsh命令
  3. 输入用户名和密码
  4. 执行CQL语句
  5. 退出CQL Shell

解决服务升级期间短暂不可用的问题

发表于 2025-06-24 分类于 go

背景

项目中有一个服务叫定价服务，用于获取价格，会被计费服务不停的调用。
注册中心由zookeeper实现
线上服务由supervisor代管

在定价服务升级的时候，由于注册中心的及时性没有那么高。就会出现，服务已经不可用（正在重启），调用端还在调用然后失败的情况

如何解决重启期间 定价服务依然可用能，达到100%的可用时间，不影响调用端？
即服务的零停机重启

解决方案

利用 github.com/jpillora/overseer 包对程序进行热更新

其核心原理是通过 多进程协作 + 文件描述符传递 实现无缝重启。

overseer原理介绍

核心架构

Master进程：

  • 常驻内存的守护进程
  • 不处理业务逻辑，只负责管理 Worker 生命周期
  • 监听重启信号（如 SIGUSR2 或文件变更）

Worker 进程：

  • 实际运行业务代码的进程（如 HTTP 服务）
  • 可被 Master 随时创建/销毁
  • 关键：继承监听套接字（Socket FD）

热重启流程

  1. 旧 Worker 运行中
    • Worker1 监听端口（如 :8080）
    • 将 Socket 文件描述符（FD）注册到 Master
  2. 触发重启
    • Master 收到 SIGUSR2 或检测到新二进制文件
    • 启动新 Worker2（加载新版本代码）
  3. FD 继承
    • Master 将保存的 Socket FD 通过 Unix Domain Socket 传递给 Worker2
    • Worker2 使用 net.FileListener 接管相同端口
  4. 双进程并行
    • 内核将新连接负载均衡到两个 Worker（SO_REUSEPORT）
    • Worker1 停止接受新连接（net.Listener.Close()）
  5. 优雅退出
    • Worker1 等待现有请求完成（可配置超时）
    • 处理完成后自动退出

KVM概述

虚拟化的定义

在计算机技术中，虚拟化意味着创建设备或资源的虚拟版本，如服务器，存储设备，网络设备，操作系统等。

虚拟化技术：

  1. 系统虚拟化
  2. 存储虚拟化
  3. 网络虚拟化
  4. GPU虚拟化
  5. 软件虚拟化
  6. 硬件支持虚拟化

系统虚拟化
这种虚拟化通常表现为在单一系统上运行多个操作系统。
这些虚拟操作系统同时运行，每个操作系统又相互独立。

虚拟化的实现方式有三种：

  1. 纯软件仿真
  2. 虚拟化翻译
  3. 容器技术

纯软件仿真

通过模拟完整的硬件环境来虚拟化来宾平台
模拟X86,ARM,PowerPC等多种CPU
效率较低
产品或方案有： QEMU,Bochs,PearPC

虚拟化层翻译

多数的虚拟化采用虚拟机管理程序Hypervisor, 其是一个软件层或子系统，也称为VMM(Virtual Machine Monitor,虚拟机监控器)
允许多种操作系统在相同的物理系统中运行
控制硬件并向来宾操作系统提供访问底层硬件的途径，向来宾操作系统提供虚拟化硬件

无硬件辅助的全虚拟化

基于二进制翻译的全虚拟化，Hypervisor运行在Ring0 ,Guest OS 运行在Ring1
通过异常，捕获，翻译 Guest OS Ring0操作
示例：

  1. VMware Workstation
  2. QEMU
  3. Virtual PC

架构简介

架构的类型：

  1. 单体架构模式
  2. 分布式架构
  3. 微服务架构
  4. 服务网格模式

不谈场景的架构设计都是耍流氓。
架构没有对不对，只有合不合适。

单体架构：

假设单体架构由于大量文件读取产生高磁盘IO,导致数据库查询慢，如何解决？

加入新组件 redis

将非事务请求的数据缓存在redis中，利用内存，解决这个问题。

带来的问题：

  1. 架构的复杂度增加
  2. 新的数据一致性问题

在架构不变的情况下解决问题

  1. Web容器层面增加拦截器阻挡垃圾重复无效的请求穿透到数据库
  2. 分析业务代码中SQL是否存在全表扫描以及索引选择性问题
  3. 增加InnoDB引擎的Buffer_Pool让查询拥有更多的缓存命中率
  4. 在操作系统层面，增加文件系统缓存，减少文件10次数

架构和框架的区别

架构指的是软件目标的宏观设计。
框架是具体实现的规则。

架构需要阐述的是：

  1. 服务器如何部署
  2. 模块如何切分
  3. 数据如何流转
  4. 带宽需要多少
  5. 人员组织，数据库集群选型是什么
